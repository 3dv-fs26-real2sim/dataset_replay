Dual Replay Discontinuity: Diagnosis & Fix Plan

Generated 2026-03-31 — for dataset_replay/scripts/test_replay.py

1. Problem Statement

When running test_replay.py --mode dual, both the left and right arms show discontinuous/jumpy motion in Isaac Sim. Single mode (--mode single) replays smoothly.

The user confirmed the discontinuity affects both arms and occurs even when the arms are not near workspace singularities.

2. Investigation Summary

2.1 Hypothesis Testing

Several hypotheses were tested and eliminated:

HypothesisResult
IK solver failures cause arms to freeze/jump Eliminated — IK has 0 failures for both arms in 400 frames
Near-workspace-boundary singularity (arm reach > 0.7 m) Eliminated — jumps occur at 0.56–0.62 m reach, well within Franka limits
Wrong quaternion convention (Q_TOOL_TO_URDF) Eliminated — both arms use the same fer_link8 frame; quaternion detection is correct for both arms
Physics simulation overriding set_joint_positions Eliminated as primary cause — single mode has larger physics discrepancy (max 0.31 rad) yet appears smooth
H5 observation data contains position discontinuities CONFIRMED — see Section 3

2.2 Diagnostic Scripts Created

Two headless Isaac Sim scripts were created to log per-frame joint values and detect discontinuities without a display:

  • dataset_replay/scripts/diagnose_dual_replay.py — runs dual mode, logs IK targets, IK results, sim read-back, and computes per-frame joint deltas. Output: dataset_replay/outputs/dual_replay_diagnosis.{npz,txt}
  • dataset_replay/scripts/diagnose_single_replay.py — same for single mode. Output: dataset_replay/outputs/single_replay_diagnosis.txt

Usage:

3. Root Cause: H5 Observation Data Discontinuities

Root cause: The dual H5 file (20250829_180500.h5) has large position jumps in its observations/qpos_arm_* streams. The script defaults to using these observations (use_actions=False), so the IK solver receives targets that jump up to 31.4 cm between consecutive frames.

3.3 Why Single Mode Is Smooth

The single-mode H5 file (20250804_104715.h5) has smooth observations/qpos_arm data (max delta = 0.010 m). So single mode replays smoothly regardless of whether actions or observations are used. The discontinuity is specific to the dual recording session.

3.4 Understanding observations/qpos vs actions

  • actions_arm_* = commanded wrist pose targets sent to the robot’s controller during teleoperation. These are smooth because the controller generates smooth trajectories.
  • observations/qpos_arm_* = measured/observed wrist poses read back from the robot’s sensors. These can have discontinuities from:
    • Task episode boundaries (robot resets between pick-and-place attempts)
    • Fast physical motions between sub-tasks
    • Sensor tracking artifacts or filter resets

4. Secondary Finding: Wrong Left Arm Warm Start

Code bug (secondary): The left arm IK warm start is initialized with the right arm’s home IK solution. This doesn’t cause the observed discontinuity but should be fixed for correctness.

In main(), home_arm_joints is computed from ik_solver_right (line 750). The same value is passed to make_ik_position_setter for the left arm (line 790) as both the initial joint positions and the IK warm start.

Affected lines in test_replay.py:

  • Line 777: q_home_left[arm_idx_left] = home_arm_joints — sets left arm physical joints to right arm’s IK solution
  • Line 790: home_arm_joints argument — initializes left arm IK warm start with right arm’s solution

5. Changes Applied

5.1 Left Arm Home IK (applied)

Applied: Compute home_arm_joints_left from ik_solver_left instead of reusing the right arm’s solution. This ensures the left arm’s IK warm-start chain begins in the correct configuration.

File: dataset_replay/scripts/test_replay.py

After the existing right-arm home IK block, a new block was added:

if args.mode == "dual":
    home_arm_joints_left, _ = solve_ik_for_pose(
        ik_solver_left, EE_FRAME_NAME_LEFT,
        WRIST_HOME_POSITION, home_wrist_quat,
    )
    if home_arm_joints_left is None:
        raise RuntimeError(
            f"IK failed for left arm home wrist pose "
            f"(pos={WRIST_HOME_POSITION}, quat={home_wrist_quat}). "
            f"Check EE_FRAME_NAME_LEFT='{EE_FRAME_NAME_LEFT}' and the Lula descriptor."
        )
    print(f"[IK] Home arm joints LEFT  (rad): {home_arm_joints_left}")

And the two lines that previously reused home_arm_joints for the left arm now use home_arm_joints_left:

# Setting initial left arm joint positions:
q_home_left[arm_idx_left] = home_arm_joints_left   # was: home_arm_joints

# Creating the left arm position setter closure:
set_left = make_ik_position_setter(
    ..., home_arm_joints_left,   # was: home_arm_joints
)

5.2 Data Source Default (NOT changed)

Not changed: The --use-actions default remains False (using observations/qpos_*). To get smooth dual replay, pass --use-actions explicitly. The discontinuity in observations/qpos_* is a property of the dual recording and is expected at task episode boundaries.

To replay smoothly:

python test_replay.py --mode dual --use-actions

6. Verification Steps

  1. Run dual mode with actions (smooth):
    python test_replay.py --mode dual --use-actions
    Both arms should move smoothly.
  2. Run dual mode with default observations:
    python test_replay.py --mode dual
    Will still show jumps at task episode boundaries (the raw observation data is inherently discontinuous at those frames).
  3. Confirm single mode unchanged:
    python test_replay.py --mode single
    Should still be smooth (single H5 observations are smooth).
  4. Check IK failure counts:
    End-of-run output should show 0 failures for both arms with both data sources.
