Overview

This script loads a pre-recorded dataset (HDF5 file) containing wrist poses and hand joint angles, opens a USD scene with one or two FER + OrcaHand robot arms in Isaac Sim, and replays the recorded trajectories. The core problem it solves: the h5 arm data is recorded as Cartesian wrist poses (position + orientation), but the simulator needs joint angles. An inverse kinematics (IK) solver bridges this gap.

The robot has two independent kinematic subsystems per arm:

  • Arm (7-DOF FER/Franka): controlled via IK — the solver finds 7 joint angles that place the end-effector frame at the target wrist pose.
  • Hand (17-DOF OrcaHand): controlled directly — the h5 hand data is joint angles already, applied as offsets from initial values.

Execution Flow

The script runs in this order:

  1. Parse CLI arguments — before anything else, because Isaac Sim's SimulationApp needs --headless at construction time.
  2. Create SimulationApp — this boots the Omniverse runtime. All Isaac Sim / Omni imports must come after this point (they depend on the runtime being initialized).
  3. Load h5 data — read arm wrist poses and hand joint angles from the HDF5 file.
  4. Detect quaternion ordering — auto-detect whether the h5 quaternions are wxyz or xyzw and reorder to wxyz if needed. The IK solver requires wxyz (scalar-first).
  5. Open USD stage — load the pre-built scene containing the robot(s) and environment.
  6. Create World and articulations — Isaac Sim's physics world, with one or two SingleArticulation objects wrapping the robot prims. If --no-collision is set, collision is disabled on the table (/World/Cube).
  7. Create IK solvers — one per arm side (different URDFs for left/right because the EE frames are in the hand portion).
  8. Compute home arm pose via IK — solve for joint angles that achieve WRIST_HOME_POSITION + WRIST_HOME_ROTATION.
  9. Resolve DOF indices — map canonical joint names (e.g. panda_joint1) to the articulation's internal DOF array indices.
  10. Set home joint positions — write the IK-computed arm joints and zero hand joints to the articulation.
  11. Create position setters — closures that, per frame, solve IK for the arm and set all joint positions.
  12. Hold home pose — render the home pose for a few seconds so the viewer can see it.
  13. Replay loop — for each frame, call the position setter with the h5 wrist pose and hand joints, step physics, optionally capture video.
  14. Report and cleanup — print IK failure stats, close video writer, close SimulationApp.

IK Solver Configuration (lines 98–120)

EE_FRAME_NAME_LEFT / EE_FRAME_NAME_RIGHT

The URDF link name that the IK solver targets. When you call compute_inverse_kinematics(frame_name=...), the solver finds joint angles that place this specific link's origin at the target position and orientation. Changing this variable changes which physical point on the robot the IK aims for.

Currently set to "fer_link8" (arm flange). Other candidates include "left_wrist_jointbody" / "right_wrist_jointbody", "connector_mount", "right_palm", "right_tower".

Important: The WRIST_HOME_ROTATION describes the desired world-frame orientation of the chosen EE frame. Different EE frames have different local coordinate axes in the URDF, so if you change the EE frame, you will likely also need to change WRIST_HOME_ROTATION to get the desired physical pose. The IK solver correctly handles the full kinematic chain — it does not need any manual rotation offset. You just need to tell it what world-frame orientation you want that particular link to have.

LULA_DESCRIPTOR_PATH / URDF_PATH_LEFT / URDF_PATH_RIGHT

The Lula IK solver requires two files: a robot descriptor YAML and a URDF. The descriptor is shared (same arm cspace for both sides), but the URDFs differ because the left and right extended URDFs contain different hand link names (left_wrist_jointbody vs right_wrist_jointbody). This means we create two separate solver instances, one per side.

WRIST_HOME_POSITION / WRIST_HOME_ROTATION

WRIST_HOME_POSITION = [0.40, 0.0, 0.3]   # meters, in world frame
WRIST_HOME_ROTATION = [[1,  0,  0],
                       [0, -1,  0],
                       [0,  0, -1]]

The target pose for the home arm configuration, solved via IK at startup. The rotation matrix is built from the rule x=[1,0,0], z=[0,0,-1] with y = z × x = [0,-1,0]. This matrix is converted to a wxyz quaternion before being passed to the solver.

HAND_HOME_JOINT_VALUES

All zeros. The hand starts fully open. Per-frame hand data is added as offsets to these values.

H5 Data Format

Arm Data — Wrist Poses (not joint angles)

Shape: (n_frames, 7) per arm. Each row: [x, y, z, qw, qx, qy, qz]

  • Columns 0–2: wrist position in meters (xyz), in the arm's coordinate frame.
  • Columns 3–6: wrist orientation as a unit quaternion. The ordering (wxyz vs xyzw) is auto-detected at runtime by detect_quaternion_order() and reordered to wxyz if needed.

These are absolute poses in the robot's base frame. The quaternion uses a tool-frame convention where identity [1,0,0,0] means the hand is pointing straight down (see Quaternion Convention below). This is converted to the URDF frame convention before being passed to the IK solver.

Hand Data — Joint Angles

Shape: (n_frames, 17) per hand. Direct joint angles in radians. Applied as offsets from HAND_HOME_JOINT_VALUES (all zeros).

Quaternion Convention: Tool Frame vs URDF Frame

The H5 wrist quaternions and the IK solver use different orientation conventions. Understanding this mismatch is critical to correct replay.

The two conventions

Tool-frame convention (H5 data)URDF convention (IK solver)
Identity quaternion [1,0,0,0] means Hand pointing straight down (Z-tool toward table) EE frame aligned with base frame (Z-up)
Hand straight down [1, 0, 0, 0] [0, 1, 0, 0]   (= Rx(180°))

Why the 180° offset exists

In the URDF kinematic chain, fer_link8 (the Franka flange) inherits its Z-axis from the last joint axis. When all joints are at zero, this Z-axis points roughly upward (away from the table). A hand pointing straight down therefore requires a 180° rotation around X to flip the frame upside-down: the rotation matrix [[1,0,0],[0,-1,0],[0,0,-1]], or equivalently the quaternion [0, 1, 0, 0] (Rx(180°) in wxyz).

Robot teleoperation systems typically define the "neutral" tool pose as the gripper pointing downward — the most common working orientation. In this convention an identity quaternion already means "hand down", so small task deviations (tilting to pick an object, rotating to pour) are represented as small rotations near identity. The Egoverse dataset follows this convention.

The conversion

Before passing an H5 quaternion q_h5 to the IK solver, we left-multiply by Rx(180°):

Q_TOOL_TO_URDF = [0, 1, 0, 0]          # Rx(180°) in wxyz
q_urdf = quat_multiply(Q_TOOL_TO_URDF, q_h5)

This is implemented by tool_quat_to_urdf() and is applied inside set_positions() (the per-frame closure returned by make_ik_position_setter()).

Numerical example

Consider the H5 first frame for arm_right: q_h5 ≈ [0.937, 0.268, 0, 0].

  • Without conversion: the IK interprets this as Rx(41°) — the hand is nearly horizontal, pointing forward. This is visually wrong.
  • With Rx(180°) pre-multiply: [0,1,0,0] × [0.937,0.268,0,0] = [-0.268, 0.937, 0, 0], which is equivalent to Rx(149°) — the hand is pointing down and tilted ∼31° toward the table. This matches the expected picking motion.
The HOME pose is not affected. WRIST_HOME_ROTATION is defined directly in URDF convention (Rx(180°) = [[1,0,0],[0,-1,0],[0,0,-1]]), so it bypasses the H5 conversion path entirely and goes straight to the IK solver.

Lula Robot Descriptor YAML

File: pandaorca_description/lula/fer_robot_descriptor.yaml

This file tells the Lula IK solver which joints to solve for and how they relate to the URDF. The URDF describes the full robot (potentially 24+ joints including the hand), but the IK solver should only move the 7 arm joints. The descriptor is the bridge between these two views.

Field-by-field breakdown

api_version: 1.0

Format version required by Lula. Always 1.0.

cspace (configuration space)

cspace:
    - fer_joint1
    - fer_joint2
    - fer_joint3
    - fer_joint4
    - fer_joint5
    - fer_joint6
    - fer_joint7

This is the most important field. It defines the active joints — the joints the IK solver is allowed to move. The order here determines the order of the joint position array returned by compute_inverse_kinematics() and expected by compute_forward_kinematics().

All other joints in the URDF (hand joints, fixed joints, etc.) are treated as locked at their default values. This means the solver can compute forward kinematics through the full chain (arm + connector + hand) to reach frames like right_wrist_jointbody, but it only varies the 7 arm joints to get there.

root_link: base

The URDF link that serves as the fixed base of the kinematic chain. Must match a <link name="..."> in the URDF. For the FER arm, this is base (the parent of fer_link0 via a fixed joint).

default_q

default_q: [0.00, -1.3, 0.00, -2.87, 0.00, 2.00, 0.75]

Default joint configuration used as a fallback seed when no warm-start is provided. This is a Franka "home-ish" pose that keeps the arm in a reasonable configuration and avoids singularities.

acceleration_limits / jerk_limits

Dynamic limits per joint. Not directly used by the IK solver (which only cares about position limits from the URDF), but required by other Lula components like RMPflow trajectory generation. Taken from the standard Franka Panda descriptor shipped with Isaac Sim.

cspace_to_urdf_rules: []

Rules for URDF joints that are not in the cspace. For example, a Franka Panda with a gripper would have {name: panda_finger_joint1, rule: fixed, value: 0.025} to lock the fingers at a fixed opening. Our FER arm doesn't have gripper joints in the arm URDF (the hand is separate), so this is empty. All non-cspace joints default to 0.

Why it exists (and when to change it)

The URDF alone is not enough for IK because it doesn't specify which joints are "active" vs "passive". A 24-DOF URDF has too many degrees of freedom — the solver needs to know that only 7 of them should move. The descriptor provides this information.

You need to regenerate or edit this file if:

  • The URDF joint names change (e.g. fer_joint* becomes something else).
  • The base link name changes.
  • You want to add the hand joints to the IK cspace (unusual but possible).

Use generate_lula_description.py to regenerate it from the URDF.

IK Solver — How It Works

The script uses LulaKinematicsSolver from isaacsim.robot_motion.motion_generation.lula.kinematics.

Initialization

At construction, Lula:

  1. Parses the URDF to build the full kinematic tree (all links and joints).
  2. Reads the descriptor YAML to identify which joints are active (the cspace).
  3. Locks all non-cspace joints at their default values (0 unless overridden by cspace_to_urdf_rules).
  4. Builds internal data structures for fast FK and IK computation.

Because the left and right arms use different URDFs (the hand portion has different link names), we create two solver instances: ik_solver_right and ik_solver_left. They share the same descriptor (same 7 arm joints), but each can resolve its own EE frame name.

Solving IK: compute_inverse_kinematics()

Given a target position (xyz) and orientation (wxyz quaternion) for a named frame, the solver finds 7 joint angles that place that frame at the target. It uses a two-phase approach:

  1. Cyclic Coordinate Descent (CCD) — a fast iterative method that adjusts one joint at a time to reduce the error. Produces a rough solution quickly.
  2. BFGS refinement — a second-order quasi-Newton optimizer that polishes the CCD solution to high precision.

The solver also accepts a warm_start parameter: an initial joint configuration to start from. By passing the previous frame's solution as the warm start for the next frame, we get:

  • Speed: fewer iterations needed because the starting point is already close.
  • Continuity: solutions don't jump between different IK branches across frames.

Orientation Convention

The Lula solver uses wxyz quaternions (scalar-first). Internally it converts them to 3×3 rotation matrices via isaacsim.core.utils.numpy.rotations.quats_to_rot_matrices(). The target orientation describes the desired rotation of the named frame in the world frame (or more precisely, relative to the USD stage origin).

Stage Units

Lula internally accounts for the USD stage unit scale. Isaac Sim defaults to meters (scale = 1.0), which matches the URDF and the h5 data. If your stage uses centimeters, the solver auto-converts.

Function-by-Function Reference

create_ik_solver(urdf_path, label)

Constructs a LulaKinematicsSolver from the shared descriptor YAML and the given URDF. Prints the active joints and all available frames (useful for choosing EE_FRAME_NAME). Called twice in dual mode (once per side), once in single mode.

rotation_matrix_to_wxyz(rot_matrix)

Converts a 3×3 rotation matrix to a wxyz quaternion. Uses scipy.spatial.transform.Rotation which returns xyzw, then reorders to wxyz for the Lula solver.

quat_multiply(q1, q2)

Hamilton quaternion product q1 × q2, both in wxyz convention. Used by tool_quat_to_urdf() to apply the Rx(180°) convention offset.

tool_quat_to_urdf(q_tool_wxyz)

Converts a quaternion from the H5 tool-frame convention (identity = hand down) to the URDF convention by left-multiplying with Q_TOOL_TO_URDF = [0, 1, 0, 0] (Rx(180°)). See Quaternion Convention for a full explanation.

detect_quaternion_order(arm_data, label)

Heuristic to determine whether h5 quaternion columns are wxyz or xyzw. Compares the mean absolute value of column 3 vs column 6 — for rotations near identity, the scalar component w ≈ 1.0 dominates. If xyzw is detected, the data is reordered to wxyz.

solve_ik_for_pose(solver, ee_frame_name, position, orientation_wxyz, warm_start)

Thin wrapper around solver.compute_inverse_kinematics(). Returns (joint_positions, success) where joint_positions is None if the solver did not converge.

setup_articulation(prim_path, world)

Creates a SingleArticulation from a USD prim path, generates a unique name from the path (replacing / with _), and adds it to the physics world's scene. Returns the articulation object.

print_dof_info(label, art)

Debug helper that prints all DOF names and indices for an articulation. Useful for verifying that the URDF/USD loaded correctly and that joint names match expectations.

resolve_dof_indices(art, names, label)

Maps a list of canonical joint names to the articulation's internal DOF array indices. This is necessary because the articulation's DOF order may not match the order in our name lists. The function tries three matching strategies in order:

  1. Exact match — look up the name directly in the articulation's DOF name list.
  2. Alias match — try panda_joint* ↔ fer_joint* substitution. The USD may use either naming convention depending on how it was exported.
  3. Suffix match — if a DOF name ends with the target name, accept it. This handles cases where the USD prepends a namespace prefix (e.g. robot/left_wrist matches left_wrist).

Returns a numpy array of integer indices that can be used to slice into art.get_joint_positions().

_read_dataset(f, candidates, required)

Tries each key in candidates against the h5 file. Returns the first match as a numpy array. If required=True and nothing matches, raises KeyError.

load_h5(path, use_actions, mode)

Loads all arm and hand datasets from the h5 file. In dual mode, loads left and right separately. In single mode, tries right-specific keys first, then falls back to generic keys (e.g. actions_arm). Validates shapes against N_ARM_POSE_DIMS and N_HAND_DOFS. Returns a dict with keys "arm_left", "arm_right", "hand_left", "hand_right", "n_frames".

make_ik_position_setter(art, arm_idx, hand_idx, ik_solver, ee_frame_name, hand_home, home_arm_joints)

This is the core function. It returns a closure (set_positions) that captures all the setup state and is called once per frame during replay.

Internal state (captured in the closure):

  • base — snapshot of all joint positions at creation time. Used as a template each frame.
  • buf — mutable buffer that gets filled per frame and written to the articulation.
  • state["prev_arm_joints"] — the last successful IK solution. Used as warm-start for the next frame, and as a fallback if IK fails.
  • state["ik_failures"] — count of frames where IK did not converge.

The returned set_positions(wrist_pose, q_hand) function:

  1. Splits wrist_pose into position (xyz) and orientation (wxyz quaternion), then converts the quaternion from tool-frame to URDF convention via tool_quat_to_urdf() (see Quaternion Convention).
  2. Calls solve_ik_for_pose() with the previous solution as warm-start.
  3. If IK succeeds: writes the new arm joints to buf and updates prev_arm_joints.
  4. If IK fails: increments the failure counter and reuses the previous solution (arm holds steady).
  5. Writes hand_home + q_hand to the hand DOF indices.
  6. Calls art.set_joint_positions(buf) to apply everything to the articulation.

A get_ik_failure_count() method is attached to the closure for reporting after replay.

The main() Function

Detailed walkthrough of main() (starting at line 686):

Step 1: Load and validate data

data = load_h5(H5_PATH, args.use_actions, args.mode)
data["arm_right"] = detect_quaternion_order(data["arm_right"], "arm_right")
# ... same for arm_left if not None

Loads arm wrist poses and hand joint angles from the h5 file. Quaternion ordering is auto-detected and reordered to wxyz if needed. The first frame is printed as a diagnostic.

Step 2: Open scene and create articulations

omni.usd.get_context().open_stage(str(USD_PATH))
world = World()
franka_right = setup_articulation(FRANKA_RIGHT_PATH, world)
world.reset()

World() creates the physics simulation. world.reset() initializes all articulations to their default state and must be called before reading or writing joint positions.

Step 3: Create IK solvers

ik_solver_right = create_ik_solver(URDF_PATH_RIGHT, "right")
ik_solver_left  = create_ik_solver(URDF_PATH_LEFT, "left")  # dual only

Two solver instances because the URDFs differ (left vs right hand link names).

Step 4: Compute home arm joints

home_wrist_quat = rotation_matrix_to_wxyz(WRIST_HOME_ROTATION)
home_arm_joints, _ = solve_ik_for_pose(
    ik_solver_right, EE_FRAME_NAME_RIGHT,
    WRIST_HOME_POSITION, home_wrist_quat,
)
# In dual mode, a separate home IK is computed for the left arm:
home_arm_joints_left, _ = solve_ik_for_pose(
    ik_solver_left, EE_FRAME_NAME_LEFT,
    WRIST_HOME_POSITION, home_wrist_quat,
)

The rotation matrix is converted to a wxyz quaternion, then IK is solved for the right solver. In dual mode, a separate home IK is also computed for the left arm using its own solver (ik_solver_left). Each arm’s home solution is used as the initial warm start for its respective IK closure, ensuring the warm-start chain begins in the correct configuration for each arm. If either IK fails, the script raises a RuntimeError with diagnostic info.

Step 5: Resolve DOF indices and set home positions

For each articulation, resolve_dof_indices() maps the canonical joint names to the articulation's internal DOF array. Then the IK-computed arm joints and zero hand joints are written directly.

Step 6: Create position setter closures

set_right = make_ik_position_setter(
    franka_right, arm_idx_right, hand_idx_right,
    ik_solver_right, EE_FRAME_NAME_RIGHT,
    HAND_HOME_JOINT_VALUES, home_arm_joints,
)
# In dual mode, the left arm uses its own home IK solution:
set_left = make_ik_position_setter(
    franka_left, arm_idx_left, hand_idx_left,
    ik_solver_left, EE_FRAME_NAME_LEFT,
    HAND_HOME_JOINT_VALUES, home_arm_joints_left,
)

These closures are the per-frame workhorses. Each one captures its own IK solver, DOF indices, and warm-start state. The home_arm_joints / home_arm_joints_left argument initializes the warm-start chain for each arm independently.

Step 7: Home hold

Runs HOME_HOLD_SECONDS × fps simulation steps with the home pose, so the viewer can see the starting configuration before replay begins.

Step 8: Replay loop

for frame_idx in range(n_frames):
    set_left(data["arm_left"][frame_idx], data["hand_left"][frame_idx])   # dual only
    set_right(data["arm_right"][frame_idx], data["hand_right"][frame_idx])
    world.step(render=True)

Each call to set_left/set_right internally solves IK, updates all joints, and the world.step(render=True) advances physics and renders the frame. Progress is printed every 100 frames. Ctrl-C cleanly exits the loop.

Step 9: Report and cleanup

IK failure counts are printed per arm. The video writer is closed. simulation_app.close() shuts down the Omniverse runtime.

Video Capture System

When --record is passed, the script captures viewport frames to an MP4 via imageio. This involves several internal functions:

  • setup_capture() — creates the imageio writer and gets the active viewport.
  • capture_frame_to_writer() — uses capture_viewport_to_buffer() with a callback that receives the raw pixel data. The callback goes through multiple decode strategies because different Kit/Isaac Sim versions provide the data in different formats (numpy array, memoryview, raw pointer, PyCapsule).
  • _buffer_to_numpy_1d() — converts various buffer types to a flat uint8 numpy array, including handling raw C pointers via ctypes.
  • _decode_raw_with_dims() — reshapes a flat buffer into an HxWx3 image given known dimensions.
  • _wait_capture_completion() — handles both sync and async capture APIs.
Recording works but is slow — each frame requires a GPU readback and encode step.

Troubleshooting

IK fails for the home pose

RuntimeError: IK failed for home wrist pose
  • Check the printed "Available frames" list — your EE_FRAME_NAME_* must appear there.
  • Verify the target pose is within the arm's workspace (roughly a 0.85m sphere around the base).
  • Ensure root_link in the YAML matches the URDF's base link name (should be base).
  • If you changed EE_FRAME_NAME, you likely also need to change WRIST_HOME_ROTATION to match the new frame's local axes.

Awkward/wrong home pose

  • WRIST_HOME_ROTATION describes the desired world-frame orientation of the EE link. Different links have different local axes. Use the IK solver's compute_forward_kinematics() to inspect what orientation a given frame has at a known joint config, then work backwards to determine the right rotation matrix for your desired physical pose.

High IK failure rate during replay

  • A few failures at extreme poses are normal. The arm holds its last valid configuration.
  • Many failures may indicate the h5 poses are in a different coordinate frame than expected.
  • Check quaternion norm in the diagnostic output — values far from 1.0 mean the data format is wrong.

Imports fail before SimulationApp

  • Any omni.* or isaacsim.core.* import placed before SimulationApp(...) will crash. Keep the two import blocks separated.
