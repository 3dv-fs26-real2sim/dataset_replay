1. The Problem in Detail

You have two data sources driving the replay:

SourceDrivesQuality
H5 file (joint trajectories)Robot arm + hand jointsHigh (recorded from real robot)
NPZ file (6D pose estimation)Object position + orientationNoisy — cm-level errors, jitter, occasional outliers

What Goes Wrong with Kinematic Replay

In the current kinematic mode, the object is a kinematic rigid body — its pose is set directly each frame via set_object_world_pose(). Physics cannot push it, gravity doesn't affect it, and it teleports to wherever the 6D estimate says. This causes:

  • Table penetration: Noisy Z estimates place the object below the table surface
  • Robot penetration: Object appears inside the robot hand/fingers
  • Floating: Object hovers in mid-air when the hand isn't nearby
  • Jitter: Frame-to-frame noise causes the object to vibrate unrealistically
  • No drop physics: When the hand opens, the object stays frozen at its last estimated pose

What "Dynamic Replay" Should Achieve

  • Object approximately follows the estimated trajectory (it's our best guess of where it was)
  • Object cannot penetrate the table, robot, or other surfaces
  • Object falls under gravity when nothing supports it
  • Noise and jitter are dampened — object moves smoothly
  • The trajectory acts as a soft guide, not a hard constraint
The Core Tension You want the object to follow a reference trajectory (pose estimation) while simultaneously obeying physics. These two goals conflict when the estimated pose is physically impossible (inside a table, inside a hand). The question is: how do you balance trajectory-following against physics compliance?
Kinematic Replay Dynamic Replay (Goal) ───────────────── ───────────────────── Estimated pose ──→ Object pose Estimated pose ──→ Tracking force ──→ Physics ──→ Object pose (exact copy) ↑ Collisions, Gravity, Contact forces Result: Penetrations, jitter Result: Smooth, physically plausible motion

2. Isaac Sim / PhysX Physics Primer

Understanding what PhysX gives us is essential for evaluating approaches. Isaac Sim wraps NVIDIA PhysX 5, which supports several mechanisms for controlled object motion:

Rigid Body Types in PhysX

TypeGravityCollisionsCan Be PushedPose Control
Static NoYes (immovable)NoNone (fixed)
Kinematic NoYes (pushes others)NoDirect (teleport)
Dynamic YesYes (full)YesVia forces/velocities

Currently your object uses Kinematic. For dynamic replay, it needs to be Dynamic so that gravity and collisions actually affect it.

Key PhysX Features for Trajectory Tracking

D6 Joint

A configurable 6-DOF joint that can connect two bodies (or one body to the world). Each of the 6 DOFs (3 translational, 3 rotational) can independently be set to locked, limited, or free, and can have a spring-damper drive that pulls toward a target position/orientation.

External Forces & Torques

RigidBodyAPI allows applying forces and torques to dynamic bodies each simulation step. You can implement your own PD controller this way.

Velocity Control

You can set linear and angular velocity on dynamic bodies. The physics engine integrates this and resolves collisions. Less precise than force control but simpler.

3. Approaches

Option A: D6 Joint with Spring-Damper Drives Recommended

Core idea: Spawn a kinematic anchor (invisible) that follows the estimated trajectory exactly, and connect the dynamic object to it via a D6 joint with spring-damper drives on all 6 DOFs. The anchor pulls the object toward the estimated pose; physics (gravity, collisions) pushes back.

Kinematic Anchor (invisible, follows trajectory exactly) │ │ D6 Joint (spring Kp + damper Kd on all 6 DOF) │ ← drives object toward anchor pose ▼ Dynamic Object (has mass, gravity, collisions) │ ├── Pushed up by table contact ├── Held by friction when grasped └── Falls under gravity when released

How It Works

1
Spawn the object as a dynamic rigid body (not kinematic). Enable gravity, collision, set a reasonable mass.
2
Create an invisible kinematic anchor prim (a tiny invisible sphere or xform). This follows the NPZ trajectory exactly, frame by frame — just like the current kinematic object.
3
Create a D6 joint connecting the anchor to the object. Set all 6 DOFs to "free" with spring-damper drives:
  • stiffness (Kp) — how hard the spring pulls toward the target
  • damping (Kd) — how much it resists velocity (prevents oscillation)
4
Each frame: update the anchor's pose from the trajectory. The D6 drive automatically generates forces pulling the dynamic object toward the anchor. PhysX resolves these against gravity + collision contacts.

Stiffness Tuning — The Key Knob

Kp (Stiffness)BehaviorWhen to Use
Very High (10⁵+)Nearly kinematic — tracks trajectory tightly, may still penetrate brieflyHigh-confidence pose estimates
Medium (10²–10³)Soft tracking — follows trajectory but yields to collisions, smooth motionNoisy estimates (your case)
Low (10⁰–10¹)Loose follow — mostly physics-driven with gentle pull toward trajectoryVery noisy or unreliable estimates
ZeroPure physics — object ignores trajectory entirelyFree-fall after release
Adaptive Stiffness You could vary Kp over time: high stiffness during confident tracking phases, zero during release/drop phases. This gives you precise control over when the object follows the estimate vs. when it follows physics.

Isaac Sim / USD Implementation

from pxr import UsdPhysics, PhysxSchema

# 1. Create anchor prim (invisible kinematic body)
anchor_path = "/World/spawned_objects/pose_anchor"
anchor_prim = UsdGeom.Xform.Define(stage, anchor_path)
UsdPhysics.RigidBodyAPI.Apply(anchor_prim.GetPrim())
rb = UsdPhysics.RigidBodyAPI(anchor_prim.GetPrim())
rb.CreateKinematicEnabledAttr(True)

# 2. Create D6 joint
joint_path = "/World/spawned_objects/tracking_joint"
joint = UsdPhysics.Joint.Define(stage, joint_path)
joint.CreateBody0Rel().SetTargets([anchor_path])
joint.CreateBody1Rel().SetTargets([object_prim_path])

# 3. Configure drives on all 6 DOFs
for axis in ["transX", "transY", "transZ", "rotX", "rotY", "rotZ"]:
    drive = UsdPhysics.DriveAPI.Apply(joint.GetPrim(), axis)
    drive.CreateTypeAttr("force")         # force-based drive
    drive.CreateStiffnessAttr(500.0)      # Kp — tune this
    drive.CreateDampingAttr(100.0)         # Kd — tune this
    drive.CreateTargetPositionAttr(0.0)    # target = anchor pose (offset 0)

# 4. Per-frame: update anchor pose (same as current set_object_world_pose)
set_object_world_pose(stage, anchor_path, traj_world[frame_idx])

Pros

  • PhysX-native — runs entirely inside the physics engine, no per-frame Python force computation
  • Collision resolution is automatic and robust
  • Smooth motion from spring-damper dynamics (natural low-pass filter on noisy input)
  • Tunable: one parameter (Kp/Kd ratio) controls the tracking-vs-physics balance
  • Object falls naturally when anchor stops moving (or stiffness goes to zero)
  • Minimal code change — anchor follows existing trajectory logic
  • Well-documented in NVIDIA Isaac Sim tutorials

Cons

  • Tuning Kp/Kd is trial-and-error for each object mass and scenario
  • Very high stiffness can cause instability (PhysX step size matters)
  • Joint setup requires additional USD prims and API calls
  • Rotational drives in D6 joints can be tricky (gimbal lock, wrapping)

Option B: Force/Torque PD Tracking Controller Good Alternative

Core idea: Make the object dynamic and apply computed forces/torques each physics step to drive it toward the estimated pose. Essentially, you implement the spring-damper in Python instead of using D6 joints.

Each physics step: target_pose = trajectory[frame_idx] # from NPZ current_pose = get_object_world_pose() # from physics error = target_pose - current_pose # position + orientation error force = Kp * pos_error - Kd * velocity # PD control torque = Kp * rot_error - Kd * ang_velocity # PD control apply_force_and_torque(object, force, torque)

PD Controller Equations

# Position PD
pos_error = target_pos - current_pos
force = Kp_pos * pos_error - Kd_pos * linear_velocity

# Orientation PD (using quaternion error)
q_error = q_target * q_current.inverse()
# Extract rotation vector (axis * angle)
rot_error = 2 * q_error.xyz * sign(q_error.w)  # assumes small angle
torque = Kp_rot * rot_error - Kd_rot * angular_velocity

# Apply to rigid body
rigid_body.apply_force(force)
rigid_body.apply_torque(torque)

Isaac Sim Implementation

from omni.physx import get_physx_interface

# In the per-frame loop, after getting target from trajectory:
rigid_body_api = UsdPhysics.RigidBodyAPI(object_prim)

# Get current state from Isaac Sim
xformable = UsdGeom.Xformable(object_prim)
current_transform = xformable.ComputeLocalToWorldTransform(Usd.TimeCode.Default())

# Or via Isaac Sim rigid body view:
from isaacsim.core.prims import RigidPrim
obj = RigidPrim(prim_path=object_prim_path)
pos, quat = obj.get_world_pose()
lin_vel = obj.get_linear_velocity()
ang_vel = obj.get_angular_velocity()

# Compute PD forces
force = Kp * (target_pos - pos) - Kd * lin_vel
torque = Kp_rot * quat_error(target_quat, quat) - Kd_rot * ang_vel

obj.apply_force(force)
obj.apply_torque(torque)

Pros

  • Full control over the tracking law — can implement adaptive, nonlinear, or state-dependent control
  • Easy to add features: force limits, deadbands, dynamic Kp scheduling
  • No extra USD prims (no anchor, no joint)
  • Conceptually simple — standard PD control
  • Can clamp forces to prevent instability

Cons

  • Runs in Python per-step — slower than D6 joint (which runs in PhysX C++)
  • Orientation error computation is non-trivial (quaternion math, singularities)
  • Must tune Kp/Kd relative to object mass and simulation timestep
  • Risk of instability if Kp is too high relative to dt (need dt-aware gains)
  • Must correctly handle frame conventions (world vs. body frame torques)

Option C: Velocity-Based Tracking Moderate

Core idea: Each frame, compute the velocity that would move the object from its current pose toward the target pose, and set that as the object's velocity. PhysX integrates the velocity and handles collisions.

# Each frame:
pos_error = target_pos - current_pos
desired_vel = alpha * pos_error / dt   # alpha in [0,1] blends tracking speed

# Clamp to prevent teleportation
desired_vel = np.clip(desired_vel, -max_vel, max_vel)

rigid_body.set_linear_velocity(desired_vel)
rigid_body.set_angular_velocity(desired_ang_vel)

Pros

  • Very simple to implement
  • Natural velocity clamping prevents large jumps
  • Collision response is decent (PhysX modifies velocity on contact)

Cons

  • Overriding velocity every frame fights the physics engine — can cause jitter at contacts
  • Gravity effect is partially overridden (you're setting velocity, not adding to it)
  • No natural damping — object doesn't settle smoothly
  • PhysX may not handle sudden velocity changes well at collision boundaries
  • Less physically principled than force-based approaches

Option D: Hybrid Kinematic-Dynamic Mode Switching Practical

Core idea: The object is kinematic when it's being grasped (follows trajectory exactly) and dynamic when released (falls under gravity, collides with table). You detect the grasp/release transition from the hand joint data.

Timeline: ──────────────────────────────────────────────────────────── KINEMATIC │ DYNAMIC │ KINEMATIC │ DYNAMIC (grasped) │ (released) │ (grasped) │ (released) │ falls, │ │ │ bounces │ │ ──────────────────────────────────────────────────────────── grasp opens grasp closes grasp opens

Grasp Detection

You already have hand joint trajectories. You can detect grasp state by:

  • Joint threshold: If finger joints are closed past a threshold, object is grasped
  • Proximity + closure: Object is within N cm of palm AND fingers are closing
  • Manual annotation: Mark grasp/release frames in the NPZ or a sidecar file
# Detect grasp from hand joint positions
def is_grasped(hand_joints, threshold=0.5):
    """Check if fingers are closed enough to indicate a grasp."""
    finger_closure = np.mean(hand_joints[finger_indices])
    return finger_closure > threshold

# Mode switching
for frame_idx in range(n_frames):
    grasped = is_grasped(data["hand_right"][frame_idx])

    if grasped and not was_grasped:
        # Switch to kinematic
        switch_to_kinematic(object_prim)
    elif not grasped and was_grasped:
        # Switch to dynamic — inherit current velocity
        switch_to_dynamic(object_prim, current_velocity)

    if grasped:
        set_object_world_pose(stage, object_prim, traj_world[frame_idx])
    # else: physics handles it

    was_grasped = grasped

Pros

  • Conceptually clean — kinematic when held, dynamic when free
  • No spring tuning needed during grasp phase (exact tracking)
  • Natural drop physics when released
  • Relatively simple implementation
  • Can combine with Option A (D6 drive during grasp, free during release)

Cons

  • Grasp detection from joint thresholds is fragile — different objects have different grasp signatures
  • Mode switch can cause discontinuities (kinematic object suddenly has mass and velocity)
  • During kinematic phase, still has penetration issues with noisy poses
  • Doesn't help with noise/jitter during the grasped phase
  • Transition velocity estimation is tricky (differentiate noisy trajectory?)
The Transition Problem When switching from kinematic to dynamic, you need to give the object an initial velocity. If you differentiate the noisy pose trajectory, you get a noisy velocity. The object might launch in an unexpected direction. You'd need trajectory smoothing around the transition point.

Option E: Pre-processed Trajectory Cleaning Offline

Core idea: Instead of modifying runtime physics, clean up the trajectory before replay. Use geometry and physics constraints to project the estimated poses into a physically plausible space.

Cleaning Pipeline

1
Temporal smoothing: Low-pass filter (Gaussian, Savitzky-Golay) to remove jitter from frame-to-frame noise.
2
Table penetration fix: Clamp Z coordinates to be above the table surface. For each frame, if object bottom is below table_z, push it up.
3
Robot collision fix: Use the robot's known geometry (from URDF/USD) to detect penetration and push the object out along the contact normal.
4
Gravity-aware drop: After the hand opens, switch from estimated trajectory to a ballistic trajectory (parabola under gravity from last grasped pose).
# Offline trajectory cleaning
import scipy.ndimage as ndi

def clean_trajectory(traj_world, table_z, robot_mesh):
    N = traj_world.shape[0]
    positions = traj_world[:, :3, 3].copy()  # (N, 3)

    # 1. Temporal smoothing
    for axis in range(3):
        positions[:, axis] = ndi.gaussian_filter1d(positions[:, axis], sigma=3.0)

    # 2. Table penetration — clamp Z
    object_half_height = 0.03  # depends on object
    min_z = table_z + object_half_height
    positions[:, 2] = np.maximum(positions[:, 2], min_z)

    # 3. Smooth rotations (SLERP-based)
    from scipy.spatial.transform import Rotation, Slerp
    rots = Rotation.from_matrix(traj_world[:, :3, :3])
    # ... apply rotation smoothing ...

    # Write back
    traj_clean = traj_world.copy()
    traj_clean[:, :3, 3] = positions
    return traj_clean

Pros

  • No runtime physics complexity — still uses kinematic replay
  • Deterministic — same input always gives same output
  • Can inspect and validate cleaned trajectory before replay
  • Smoothing removes jitter effectively
  • Easy to implement Z-clamping for table

Cons

  • Robot collision avoidance requires mesh-mesh intersection testing — complex offline
  • Doesn't produce realistic drop dynamics (ballistic approximation is simplistic)
  • Smoothing introduces lag and may distort the trajectory shape
  • Still fundamentally kinematic — doesn't look "physical"
  • Must be rerun when pose estimates change
  • Doesn't handle edge cases well (object rolling, bouncing)

Option F: Contact-Aware Pose Correction (Runtime) Complex

Core idea: Keep the object kinematic, but each frame, query PhysX for contacts/overlaps and adjust the pose to resolve penetrations. Essentially, use the physics engine as an oracle for collision queries without making the object truly dynamic.

How It Works

  • Set the kinematic pose from trajectory
  • Query PhysX overlap/sweep to detect penetration with environment
  • If penetrating: compute minimum translation vector (MTV) to resolve overlap
  • Apply MTV correction to the kinematic pose

Pros

  • Prevents visible penetrations
  • Maintains kinematic simplicity

Cons

  • PhysX overlap queries from Python are slow and not well-exposed in Isaac Sim
  • MTV computation with convex hulls is non-trivial
  • Still no gravity — object won't fall
  • Correction can cause visual popping (object jumps to resolved position)
  • Doesn't solve the fundamental problem of noisy trajectories
  • Most complex to implement for least gain

5. Recommended Path

Primary: Option A (D6 Joint) + elements of Option D (Hybrid)

The strongest approach combines the D6 joint's physics-native tracking with adaptive stiffness inspired by the hybrid idea:

1
D6 joint as the core mechanism. This is the most robust and performant way to make a dynamic object track a reference trajectory in PhysX. It handles collisions, gravity, and damping natively in the physics engine (C++ level), requires no per-frame Python force computation, and is well-supported in Isaac Sim.
2
Adaptive stiffness from grasp state. Instead of a hard kinematic/dynamic switch (which causes discontinuities), modulate the D6 drive stiffness:
  • During grasp: high Kp (tight tracking — object follows hand)
  • During release: Kp ramps to zero over ~10 frames (smooth transition to free fall)
  • During free flight: Kp = 0 (pure physics)
3
Optional: pair with light offline smoothing (Option E) on the input trajectory to further reduce jitter before the D6 drive sees it. A simple Gaussian filter with σ=2–3 frames costs nothing and helps.
Why not pure Option B (PD Force)? Option A and B are mathematically equivalent — a D6 drive is a PD controller running inside PhysX. But the D6 joint runs in C++ inside the solver, is timestep-aware (implicit integration), and doesn't require you to handle quaternion error math or body-frame torque application. It's strictly better unless you need a control law that D6 drives can't express (nonlinear, discontinuous, etc.).

Fallback: Option D (Hybrid) if D6 joints prove problematic

If D6 joint configuration in Isaac Sim turns out to be buggy or poorly documented for your use case, the hybrid kinematic-dynamic approach is a reliable fallback. It's simpler and more predictable, at the cost of penetration during the kinematic (grasped) phase.

Complement: Option E (Offline Smoothing) regardless of choice

A light temporal filter on the NPZ trajectory is nearly free and always helps. Apply it as a pre-processing step before any runtime approach sees the data. This is orthogonal to the runtime physics approach and should be done regardless.

7. Tuning Guide

D6 Drive Parameters

The drive force is: F = Kp * (target - current) - Kd * velocity

Starting Values (for a ~100g object like a rubber duck)

ParameterStart ValueRange to ExploreEffect of Increase
Kp (translational)50050–5000Tighter tracking, more oscillation risk
Kd (translational)10010–1000More damping, slower response, less overshoot
Kp (rotational)20020–2000Tighter orientation tracking
Kd (rotational)505–500More rotational damping
Object mass0.1 kg0.01–1.0Heavier = needs higher Kp, more inertia
Critical Damping Rule of Thumb For a mass-spring-damper, critical damping occurs at Kd = 2 * sqrt(Kp * mass). For mass=0.1 and Kp=500: Kd = 2 * sqrt(50) ≈ 14. Start there and increase Kd if you see oscillation. Over-damping (Kd >> critical) is usually fine — the object just tracks slightly behind the target.

Tuning Strategy

  1. Start with high Kp, high Kd — verify the object tracks at all
  2. Lower Kp until the object no longer penetrates the table (it yields to contact forces)
  3. Adjust Kd until oscillations stop but motion isn't sluggish
  4. Test drop: Set Kp=0 mid-trajectory and verify the object falls naturally
  5. Test collision: Verify the object slides along the table surface instead of going through it

Simulation Timestep Considerations

PhysX stability depends on the timestep. Isaac Sim defaults to 60 Hz (dt ≈ 0.0167s).

  • Very high Kp with large dt can cause the spring to overshoot and oscillate
  • If you see instability: increase physics substeps (e.g., 2–4 substeps per render frame)
  • Isaac Sim setting: PhysxSchema.PhysxSceneAPI.CreateTimeStepsPerSecondAttr(120)
  • More substeps = more stable but slower simulation

8. Failure Modes & Mitigations

Potential Issues and Solutions

1. Object oscillates or vibrates

Cause: Kp too high relative to Kd and mass. The spring overshoots each step.

Fix: Increase Kd (add more damping) or decrease Kp. Ensure Kd ≥ 2·√(Kp·mass).

2. Object doesn't track well — lags behind trajectory

Cause: Kp too low or Kd too high (over-damped).

Fix: Increase Kp. If still sluggish, reduce Kd slightly.

3. Object explodes / flies away at start

Cause: Initial pose of object and anchor are far apart, creating a huge spring force on frame 0.

Fix: Ensure object and anchor start at the same pose. Or: ramp up Kp from 0 over the first ~10 frames.

4. Object penetrates table despite being dynamic

Cause: Spring force exceeds what collision response can counter in one step.

Fix: Lower Kp, increase physics substeps, or add maxForce limit to the D6 drive.

5. Object doesn't fall when released (Kp → 0)

Cause: Gravity disabled, or mass not set, or D6 joint still has residual stiffness.

Fix: Verify DisableGravityAttr(False) for dynamic objects. Confirm Kp is truly 0.

6. Convex hull collision doesn't match visual mesh

Cause: Your objects use convex hull approximation. Concave objects (like a duck) lose internal geometry.

Fix: Use convex decomposition instead: MeshCollisionAPI.CreateApproximationAttr("convexDecomposition"). This creates multiple convex hulls that better approximate concave shapes. Slightly slower but much more accurate.

7. D6 joint rotational drives behave oddly

Cause: Quaternion wrapping / gimbal issues in the drive target computation.

Fix: The D6 drive target for rotation is always relative to the joint frame (not absolute). Since the anchor follows the trajectory and the target offset is zero, this should work. If not, try setting the rotational drive type to "acceleration" instead of "force".

Summary

Yes, dynamic replay is feasible. The D6 joint approach (Option A) is the most practical path. It's a well-supported PhysX feature, runs at C++ speed inside the physics solver, naturally smooths noisy input through spring-damper dynamics, and handles collision resolution automatically. Combined with adaptive stiffness from grasp detection (Option D's insight) and optional offline trajectory smoothing (Option E), you get a system where:

  • The object smoothly tracks the estimated trajectory when grasped
  • The object never penetrates the table or robot
  • The object falls realistically when released
  • Noise and jitter are naturally dampened
  • A single parameter (Kp/Kd ratio) controls the tracking-vs-physics balance

The main engineering effort is: spawning the anchor, creating the D6 joint with drives, and tuning the stiffness/damping parameters for your specific objects. Expect 1–2 days of implementation and 1 day of tuning.
